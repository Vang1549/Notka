# Как обновлять Нотку

Рабочий репозиторий — `Vang1549/Notka`, ветка `main`. Разработка ведётся в основной папке; `D:\Tools\Notka\build` пересоздаётся сборкой. Текущее изменение оболочки и редактора описано в [RELEASE-0.70.md](RELEASE-0.70.md).

## Что выпускать

| Изменение | Выпуск |
|---|---|
| Ноты, дорожки, интерфейс, сцена, JS-звук, экспорт без нового Android-моста | Новый ZIP редактора с подходящим minApk. |
| Стартовая панель, Android-файлы, служба, разрешения, методы моста, сертификат, адреса загрузки | Новый APK. |
| Банк или предпрослушивание | Новый asset и подписанный каталог; существующие asset неизменяемы. Редактор 0.83 запрашивает каталог при открытии библиотеки. |
| Документация, тесты | Изменение репозитория; новая сборка приложения не нужна. |

Кнопка обновления панели устанавливает APK. Панель не поставляется отдельно от оболочки.

## Версии

`source/release.json` задаёт apk_code/version, editor_code/version/name, panel_code/version, editor_min_apk и update_origin. `source/release_config.py` переносит значения в панель, экспорт, диагностику и верхнюю границу совместимости Java. Он запускается основной командой сборки и build.py; verify.py проверяет отсутствие рассогласования. Для отдельной сборки редактора сначала выполнить `python release_config.py` из source.

`editor_min_apk` означает минимальную необходимую оболочку. Пакет 83 требует APK 70 из-за новых возможностей оболочки. Для будущего редактора без изменения Android-контракта эту границу можно оставить. Версия APK проверяется отдельно от версии редактора и панели.

Новые байты требуют новых номеров. Даже повторная сборка APK может изменить ZIP-метаданные времени: публиковать нужно именно проверенные байты, а не пересобирать их после проверки. `publish_release.py` и публикатор GitHub отказываются заменять уже существующий APK другим файлом.

При изменении .notka определить чтение прежних версий, значения по умолчанию и поведение старых редакторов. Сохранять стабильные ссылки на инструменты и нынешний сертификат.

## Сборка

Из PowerShell в корне проекта:

```powershell
.\scripts\build-local.ps1
```

Подготовка среды и ключа — [LOCAL-DEVELOPMENT.md](../LOCAL-DEVELOPMENT.md). Инструменты находятся в D:\Tools\Notka, системные программы не заменяются.

Команда синхронизирует версии, подготавливает закреплённые зависимости, создаёт рабочую копию source/scripts/dist в WSL, собирает медиаэкспортёр и редактор, подписывает ZIP, компилирует Java и host.ops, собирает APK и выполняет выбранные проверки. Результаты копируются в `outputs/local-<версия>/`; подготовленный dist остаётся в D:\Tools\Notka\build\dist. Основной dist не меняется автоматически.

Не редактировать временную рабочую копию. `build.py` пишет в соседний dist/bundles, поэтому для пробных сборок использовать изолированный вход. Для редактора без APK в отдельной рабочей копии: синхронизировать версии, выполнить `node build-media.cjs`, `node build-editor.cjs`, затем `python bundle_channel.py <staging-dist> <код> <версия> <название>`.

## Проверка

Выбирать проверки по изменению согласно AGENTS.md. Полный `npm test` полезен для широких изменений; новый обязательный барьер CI не вводится.

Проверять готовую связку APK → панель → реальные метаданные встроенного редактора → передача на запуск. Эту регрессию проверяет `test-release-panel.cjs`: она также моделирует каталог с будущим несовместимым редактором. `verify.py` проверяет подпись и согласование версий.

Для звуков нужны NumPy, SciPy и FFmpeg. На этом ПК: `py -3.12 scripts/setup-sound-tests.py`, установка только в D:\Tools\Notka. Wheel-файлы и SHA-256 закреплены в sound-test-wheels.json. Тест использует NOTKA_FFMPEG, FFmpeg из PATH или бинарник imageio-ffmpeg. Остальные зависимости — `source/requirements-test.txt`.

`scripts/publish.py --verify-only` проверяет подписи каталогов, содержимое ZIP, имя репозитория, размер и SHA-256 каждого asset публикации; не обращается к GitHub для размещения файлов. Для URL-asset ему всё же требуется скачивание. Предпочитать локальные `path`.

На телефоне отдельно проверять установку, реальный WebView, системные файлы, звучание, память и кодировщики при сворачивании. Модели DOM, статические проверки Java и структура WAV не подтверждают весь пользовательский сценарий. Оригинальный Floe-пакет имеет отдельную необязательную проверку.

## GitHub и канал обновлений

APK 0.70 запрашивает каталоги, редакторы и звуки по `https://raw.githubusercontent.com/Vang1549/Notka/updates/dist`. APK скачивается по `https://github.com/Vang1549/Notka/releases/download/apk-<код>/Notka-<код>.apk`. Страница выпусков открывает GitHub Releases. Старая установка 0.69 сама этот адрес не поменяет: переход на 0.70 выполняется ручной установкой один раз.

1. Собрать и проверить кандидат. Скопировать только новые файлы и соответствующие подписанные каталоги из staging в основной dist, сохранив старые артефакты.
2. Описать выпуск в publication.json: repository, `update_branch: "updates"`, releases с tag/title/notes/latest и asset name/path/bytes/sha256. Допустимые теги публикатора — apk-<число> и archive; ZIP редактора можно приложить к APK Release.
3. Зафиксировать исходники, новые артефакты, каталоги и отчёт; отправить main. Изменение publication.json запускает `.github/workflows/publish.yml`.
4. Workflow проверяет материалы, создаёт draft Release, загружает неизменяемые файлы и публикует выпуск. Только затем он создаёт или передвигает `updates` на тот же коммит. Обновление ветки только вперёд; force не используется.
5. Проверить завершение workflow, target commit, публичные asset и активную ветку updates. Скачать channel/catalog с реального адреса и сверить подписи, размеры и хеши. CDN GitHub может обновлять кеш не мгновенно.

Обычный push main не переключает updates. При сбое размещения исправить причину и повторить публикацию; не двигать updates вручную на непроверенный кандидат. Закрытый ключ на GitHub runner не нужен. Старый Site не развёртывается и не удаляется.

## Звуки и возврат к прежнему состоянию

Готовые банки позволяют собирать приложение без повторного синтеза. Для нового банка нужны исходные записи и лицензия, новый asset/revision, аудиопроверка и подписанный каталог. Предпрослушивание — отдельный подписанный MP3. `publish_instruments.py` не создаёт preview автоматически.

`build_generaluser.py` пока фиксирует список пресетов и имена *-1. Для нового содержимого сначала задать новые идентификаторы и отдельный staging; старые банки не регенерировать поверх опубликованных. Исходный SF2 скачивается по URL и SHA-256 из sample-source/generaluser/source.json; для генерации дополнительно нужен FluidSynth. Авторские личные материалы не публикуются.

Предыдущие исходники доступны в Git, совместимые редакторы — в панели. Android обычно не принимает меньший versionCode поверх нового: исправление оболочки выпускать следующим номером. Для отмены неудачного канала создать новый коммит с проверенным каталогом и активировать через тот же порядок; не переписывать историю updates. Удаление приложения не является откатом данных.
