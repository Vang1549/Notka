## Подтверждённые проблемы

### Встроенный редактор отфильтровывается панелью

**Приоритет первый.** В опубликованном `dist/Notka-69.apk` AndroidManifest сообщает 0.69, но `assets/index.html` содержит `currentVersion=68,currentApk='0.68'`. Встроенный пакет 82 имеет `minApk=69`.

`validInfo` в `source/app/launcher.html` отказывает такой записи. `EditorStore.inventory()` может корректно установить и вернуть пакет, но панель не добавит его в доступные версии. На модели панели, запущенной с настоящими launcher и builtin metadata из опубликованного APK, получен результат:

```json
{
  "panelApkCode": 68,
  "expectedApkCode": 69,
  "builtinCode": 82,
  "builtinMinimumApk": 69,
  "builtinAccepted": false,
  "newestOfferedEditor": 71
}
```

Проблема не в восстановлении исходников или подписи ZIP. Редактор 0.82 физически присутствует и имеет корректную подпись, но цепочка выбора не допускает его к запуску. Прежний ответ об успешных проверках сборки был верен для выполненных проверок подписи и отдельных компонентов; их было недостаточно для утверждения, что приложение запускает новый редактор.

Причина пропуска: `test-bundle-panel.cjs` подставляет пакет 72 с `minApk=64`, а `verify.py` проверяет настоящий встроенный ZIP и манифест APK без проверки соответствия версии в HTML-панели. Нужна связанная проверка реального релизного содержимого. Исправление уже опубликованных байтов 0.69 недопустимо; нужен следующий APK.

### Новый каталог звуков не запрашивается из обычного интерфейса

В `library.js` есть `checkSoundCatalog()`, но ни startup, ни открытие библиотеки её не вызывают. Startup выполняет `restoreSoundCatalog()` — читает встроенную строку `shippedSoundCatalog` и уже имеющийся локальный каталог. Тест `test-catalog.cjs` вызывает проверку напрямую, поэтому зелёный тест не доказывает наличие пользовательского пути обновления.

Следствие: одного добавления нового банка и server-side catalog недостаточно, чтобы существующий редактор увидел новый инструмент. Уже известные инструменты по-прежнему могут скачиваться. Для новых позиций сейчас нужны обновлённые встроенные метаданные редактора либо восстановленный путь проверки каталога.

### Каталог редакторов отклоняется целиком при несовместимой записи

`unpackCatalog()` требует `editions.every(validInfo)`, а `validInfo` проверяет `minApk <= currentVersion`. Поэтому появление хотя бы одной записи для более нового APK отклоняет весь каталог, включая совместимые записи. Это следует непосредственно из условия; текущий дефект 68/69 дополнительно проявляет эту связь.

При будущей доработке разделить проверку структуры и подписи каталога от выбора поддерживаемых записей. Нельзя просто снять проверку minApk и запускать несовместимый код.

### Номера версий и инструкции расходятся

Диагностика внутри runtime 0.82 сообщает `editor:'0.81'`. Номер панели и границы minApk продублированы в нескольких исходниках. Старый раздел README рекомендовал класть прежний ключ в source и описывал Sites как основной путь публикации. Инструкции README уточнены в рамках исследования; исполняемый код и опубликованные артефакты не исправлялись.

## Места, требующие проверки на Android

**Ссылка FrozenPlain.** `authorLink()` создаёт обычную внешнюю ссылку, но текущий WebViewClient в `EditorStore.load()` отвечает `true` на любую навигацию и не запускает внешний браузер. В host.ops Player отдельного метода открытия этой ссылки нет. По коду переход должен блокироваться; реальный тап на устройстве ещё не проверен. `test-source-links.cjs` проверяет href и данные, а не Android-навигацию.

**Сохранение настроек медиаэкспорта.** `media-export.js` использует localStorage, но `Player:onCreate` не включает DOM storage; оно включается только у Main. Ошибки записи подавляются catch. Это основание проверить, сохраняются ли настройки экспорта между запусками в настоящем WebView; тестовая модель предоставляет работающий localStorage и не проверяет настройку оболочки.

**Ограничения платформы.** Реальные кодировщики, системная установка APK, MediaStore/выбор документов, память звуков, поведение фонового WebView и вид экранов требуют отдельного устройства. Наличие minSdk 21 само по себе их не подтверждает.

## Сборка и публикация

GitHub сейчас является основным репозиторием разработки. Workflow публикует готовые артефакты из publication.json, но не строит APK из source. Публикация GitHub не меняет зашитый в приложение старый origin и не публикует Site.

`bundle_channel.py` защищает неизменяемые ZIP от перезаписи. `publish_release.py`, напротив, копирует APK по заданному номеру без такой проверки; поэтому его следует использовать в staging и не направлять на выпущенный dist с тем же кодом. `scripts/publish.py` проверяет существующие release assets и отказывается от их замены отличающимися байтами.

Для обычной сборки исходников достаточно уже подготовленных банков. Полная регенерация звуков — отдельный процесс: необходимы исходные WAV/SF2, дополнительные библиотеки, синтезатор и кодировщик. Часть источников скачивается по закреплённым ссылкам и не хранится целиком в репозитории. Сохранённые готовые банки позволяют продолжать разработку приложения без их повторной генерации.

## Порядок дальнейшей работы

1. Исправить согласование версии оболочки и выбора встроенного редактора; проверить на настоящем составе APK, затем на телефоне.
2. Перед расширением библиотеки определить, как редактор будет получать новый каталог. Согласовать отдельную раздачу файлов с GitHub: репозиторий уже перенесён, автоматический канал пока нет.
3. Проверить внешнюю ссылку и сохранение настроек в реальном WebView; исправить подтверждённые проблемы.
4. Свести источники номеров версий и дополнить описание зависимостей звукового теста. Проверки выбирать по изменению, без нового обязательного полного CI-барьера.
5. После этого выпускать новые возможности, сохраняя совместимость .notka, нынешний ключ и неизменяемость опубликованных материалов.

Этот отчёт фиксирует найденное состояние. Он не означает, что перечисленные исправления уже внесены или выпущен новый APK.
